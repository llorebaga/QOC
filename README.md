## Running it locally

Requires Python ≥ 3.10.

```bash
pip install -r requirements.txt
python build.py --serve          # http://localhost:8000, rebuilds on every change
```

Other commands:

```bash
python build.py                  # build into _site/
python build.py --base QOC       # build for a sub-path, i.e. served under /QOC/ (GitHub Pages)
python tools/make_logo.py        # regenerate the logo and favicon
python tools/make_social_card.py # regenerate the share preview image (needs Chrome or Edge)
python tools/refs.py add KEY --doi 10.1103/...   # add a reference (metadata from Crossref/arXiv)
python tools/refs.py check       # validate the bibliography
python tools/fetch_arxiv.py --days 14            # fetch recent arXiv papers (what the daily job runs)
```

### Writing a topic article

Create `content/topics/<topic-id>.md` (the id must exist in `data/taxonomy.yaml`):

```markdown
---
updated: 2026-10-11
status: draft            # draft | reviewed
key_papers:
  - key: khaneja2005grape
    note: Why this paper matters, in one sentence.
software:
  - name: qutip-qoc
    url: https://github.com/qutip/qutip-qoc
---

Text with inline math $H(t)$, display math $$U(T) = \dots$$, citations [@khaneja2005grape]
and links to other topics [[krotov]] or [[krotov|with custom text]].
```

### Writing an open problem

Create `content/problems/<problem-id>.md` (the id is the URL, so it is permanent; lowercase words joined by `-`):

```markdown
---
title: Short name of the problem
question: >-
  The question in one or two sentences, with math $\dots$ if needed.
status: open             # open | partial | solved
topics: [control-landscapes, controllability]   # field-map topic ids
posed_by:                # the paper(s) that pose it — required
  - key: koch2022roadmap
    where: Section 2.3. How the paper states the problem.
added: 2026-10-14
updated: 2026-10-14
review: draft            # draft | reviewed
---

## Statement      (precise formulation)
## Why it matters
## Known results  (partial progress, with citations)
## Status         (why the status is what it is)
```

The build checks the status, the topic ids and every reference key.

## How the repository is organized

```
config.yaml            site settings, navigation, section descriptions
data/taxonomy.yaml     THE backbone: families and topics of the field (ids are used everywhere)
data/references.yaml   bibliography (generated by tools/refs.py)
data/papers/           arXiv archive, one JSON file per year (updated daily by CI)
content/topics/        topic articles (Markdown + LaTeX)
content/problems/      open problems (Markdown + LaTeX)
qocsite/               build helpers: Markdown/citations, paper statistics, paper selection rule
templates/             Jinja2 templates — base layout, partials, one file per page type
static/                CSS, JS, images (served as-is)
tools/                 logo generator, bibliography tool, arXiv harvester
build.py               the static-site generator
.github/workflows/     build check on push; daily arXiv update
```

### Design principles

- **Plain text first.** All content is Markdown or YAML so that domain experts can edit it
  without touching code.
- **One taxonomy.** Topic ids from `data/taxonomy.yaml` link articles, papers, groups and open
  problems. The build fails if a reference points to a topic that doesn't exist.
- **Static and dependency-light.** No Node toolchain; Python + Jinja2 at build time, vanilla JS in
  the browser, third-party libraries (KaTeX, Leaflet, D3) loaded only on pages that need them.
- **Accessible and themeable.** Light and dark themes, keyboard navigation, reduced-motion support.
